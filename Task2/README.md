# Проверочный лист бизнес-систем

Лист заполнен по кейсу и исходной схеме. «Нет» — проблема прямо указана в описании. «Нет данных» — нужно проверить на аудите.

## Системы

| Домен | Системы | Что в них важно проверить |
| --- | --- | --- |
| Продажи | Витрина, `client-crm-app`, `client-tour-app`, `client-mart-app`, `client-mart-estate-app` и их БД | Регистрацию, связь профиля с клиентом, брони и документы сделки |
| ЖКУ | Мобильное приложение, `tenant-core-app`, CRM собственников и их БД | Права на квартиру, доступ между УК, платежи и управление умным домом |
| Финансы | `accountant-service-1`, БД учёта, Active Directory | Доступ к проводкам, реквизитам и выгрузкам |
| Данные | Greenplum, S3, BI и отчётность | Доступ к сырым ПДн и состав данных в аналитике |
| Общие сервисы | Keycloak, AD, Kubernetes, ЦОД, облако и резервные копии | Учётные записи, секреты, сетевые ограничения и восстановление |
| Партнёры | УК, платёжный провайдер, госорганы; планируется умный дом | Права на чужие объекты и состав передаваемых данных |

## Выбор разделов

- Доступ: в кабинетах уже появляются чужие данные, а одна УК может обращаться к данным другой. Нужно проверить и вход в систему, и права на конкретные объекты.
- Данные: регистрации не согласованы, потоки не учтены, ограничений в DWH нет. Это мешает исправить профили и использовать данные для BI/ML.
- Интеграции: единых правил для партнёрских API нет. Подключение биометрии требует ещё и проверки правовых оснований.
- Инфраструктура: сервисы работают в своём ЦОД и облаке. Нужны границы между средами, защита Kubernetes и проверка восстановления из копий.
- Инциденты и изменения: специалист ИБ один, часть решений до него не доходит. Нужны порядок согласования изменений и понятные действия при утечке.

## Проверки

| № | Вопрос | Да/нет | Комментарий |
| --- | --- | --- | --- |
| **I** | **Управление доступом** | — | — |
| I.1 | Есть ли аутентификация пользователей? | Да, частично | На схеме есть Keycloak и AD. Проверить, все ли приложения их используют. |
| I.2 | Включена ли MFA для администраторов и критичных действий? | Нет данных | Проверить вход администратора и выдачу доступа в дом. |
| I.3 | Проверяются ли права на каждую квартиру, дом и УК? | Нет | Описан доступ к чужим данным. Подмена ID должна давать отказ при чтении и изменении. |
| I.4 | Ограничен ли доступ к DWH и BI? | Нет | По кейсу ограничений нет. Проверить роли, доступ к строкам и отдельным полям. |
| I.5 | Согласованы ли точки регистрации клиентов? | Нет | Проверить единый идентификатор, дубли и связь профиля с учётной записью. |
| I.6 | Отзываются ли права при увольнении, смене роли и собственника? | Нет данных | Проверить блокировку сессий, групп и разрешений на устройства. |
| I.7 | Разделены ли просмотр, настройка кластера и чтение секретов? | Нет данных | Проверить RBAC, доступ к чужим namespace и обход через pod/exec. |
| **II** | **Безопасность данных** | — | — |
| II.1 | Есть ли классификация и владельцы данных? | Нет данных | Согласовать категории из Task1 и сроки хранения. |
| II.2 | Учтены ли потоки между приложениями и DWH? | Нет | Потоки контролируются несистемно. Нужен список полей, целей и получателей. |
| II.3 | Используется ли шифрование при хранении и передаче? | Нет данных | Проверить TLS, настройки БД, защиту и ротацию ключей. |
| II.4 | Исключено ли смешение профилей в личном кабинете? | Нет | Есть жалобы на чужое ФИО. Проверить сессии, кеш и связи записей двух клиентов. |
| II.5 | Выполняется ли резервное копирование всех БД? | Да | Указано в кейсе. Запросить журналы копирования. |
| II.6 | Проверяется ли восстановление и защита самих копий? | Нет данных | Восстановить копию в отдельной среде; проверить целостность, шифрование и права доступа. |
| II.7 | Ограничены ли ПДн в тестах, аналитике и логах? | Нет данных | Проверить выгрузки, обезличивание и отсутствие лишних полей. |
| II.8 | Исправляются и удаляются ли данные по установленным правилам? | Нет данных | Проверить сроки хранения, запросы на удаление и обработку восстановленных копий. |
| **III** | **Внешние интеграции** | — | — |
| III.1 | Есть ли единые правила безопасности API партнёров? | Нет | Их отсутствие указано в кейсе. Нужны проверка контрактов и тесты отказа в доступе. |
| III.2 | Передаются ли только необходимые данные? | Нет | Контракты раскрывают ПДн. Проверить поля ответов и запрет изменения служебных атрибутов. |
| III.3 | Проверены ли основания обработки и договоры с партнёрами? | Нет данных | Сверить цели, состав ПДн и поручения на обработку с 152-ФЗ. |
| III.4 | Проверены ли размещение данных и схема биометрии? | Нет данных | Уточнить страны хранения, применимость 572-ФЗ, согласия и доступ без распознавания лица. |
| **IV** | **Защита инфраструктуры** | — | — |
| IV.1 | Есть ли межсетевой экран для внешнего доступа? | Да, частично | Firewall указан. Его правила и исходящую фильтрацию нужно проверить. |
| IV.2 | Разделены ли домены, тестовые среды и партнёрские подключения? | Нет данных | Проверить маршруты, firewall, NetworkPolicy и поддержку политик со стороны CNI. |
| IV.3 | Закрыты ли служебные порты и Kubernetes API? | Нет данных | Проверить внешний доступ, kubeconfig и отсутствие анонимного доступа. |
| IV.4 | Выполняются ли обновления и поиск уязвимостей? | Нет данных | Проверить ОС, образы, зависимости и прошивки устройств. |
| **V** | **Инциденты и изменения** | — | — |
| V.1 | Получает ли ИБ изменения, влияющие на безопасность? | Нет | Передача решений нарушена. Нужен ответственный от каждого домена и согласование новых интеграций. |
| V.2 | Есть ли аудит действий и оповещения? | Нет данных | Проверить запись входа, решения о доступе и команды партнёру без секретов в логах. |
| V.3 | Есть ли план действий при раскрытии чужих данных? | Нет данных | Проверить блокировку ошибочного доступа, сохранение доказательств и порядок уведомления РКН. |

Правовые основания: [152-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_61801/) и [572-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_436110/).
